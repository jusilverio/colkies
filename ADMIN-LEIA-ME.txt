COOLKIES — VERSÃO DE VALIDAÇÃO MYSQL (NÃO LIBERAR VENDAS)

1. Preserve um backup da versão atualmente publicada. Extraia este ZIP em uma pasta separada.
2. A conexão usa DATABASE_URL (MYSQL_PUBLIC_URL do Railway), já configurada pela proprietária na Netlify. Nunca coloque credenciais no código, GitHub ou arquivos públicos.
3. Configure também COOLKIES_ADMIN_PASSWORD, segredo aleatório de no mínimo 20 caracteres, no ambiente do deploy de teste. Se já existir, mantenha a senha. Não compartilhe seu valor.
4. O projeto precisa ser publicado via Git/Netlify com build de Functions e instalação das dependências npm, não por arrastar somente a pasta public. Node 22 recomendado. A pasta publicada é public; não exponha o código de servidor ou a base de CEPs.
5. Use ambiente de teste protegido, não substitua a loja pública antes de validar. Deploys de teste precisam de variáveis próprias (preferencialmente banco de teste separado). Se não disponíveis, não faça testes que modifiquem dados de produção.
6. Abra /admin.html, entre com a senha. O backend cria 7 tabelas e inicializa catálogo e configurações. No login administrativo, importa os 19.687 CEPs atendidos da tabela anterior em transação, com marcador de migração para não duplicar os registros. Não importa os CEPs sob consulta. A conexão exige TLS com validação do certificado. Se o Railway não oferecer TLS confiável para o endpoint público, será preciso configurar CA/certificado ou uma arquitetura de rede privada; não desative a validação. MYSQL_SSL_CA é opcional para uma CA confiável fornecida pelo serviço. A conexão ainda não foi validada.
7. Confira catálogo, tarifas, datas e edição de produtos. A base de CEPs contém estimativas anteriores, não rotas verificadas; valide amostras antes de vender. Os limites padrão são 5 pedidos por horário, 60 cookies por dia, reserva de 15 minutos.
8. Não tente cobrar: checkout, webhook e status de pagamento foram desativados explicitamente nesta versão. A biblioteca orders.mjs tem lógica de reserva e confirmação transacional ainda não exposta nem testada em MySQL. Não é suficiente ativar ENABLE_REAL_PAYMENTS. A integração InfinitePay precisa ser concluída e testada, incluindo confirmação independente, pagamentos tardios, idempotência, estorno e falhas de link.
9. Pendências: limitar tentativas de autenticação, credenciais de banco de menor privilégio, backups e restauração, migração de eventuais pedidos anteriores em Blobs, testes de concorrência, testes de UI e implantação, estoque e custos, assinatura recorrente, privacidade/LGPD e paginação do painel (limite inicial de 1000 pedidos). O catálogo está armazenado em JSON no MySQL, com IDs estáveis; não há exclusão de produtos. Clientes aparecem no painel a partir de pedidos pagos. Produção só inclui pedidos pagos. Não há cálculo de lucro líquido.

Validação realizada: node --check em arquivos JS/MJS e scripts HTML; 3 testes unitários de regras. Não houve instalação da dependência mysql2, execução SQL em servidor, publicação ou teste ponta a ponta.
